### Findings

#### AUD-006-SEC001 — Medium — In a field made with `Field::binary`, products and inverses branch on the bits of an operand, so the time to check or correct a word depends on its symbols

- **Category:** SEC.
- **Severity:** medium.
- **Status:** open.
- **Release blocking:** false.
- **Affected files and builds:** src/field/binary.rs:51-63 (`multiply`) and 67-77 (`inverse`), reached through `Field::multiply` and `Field::inverse` (src/field.rs:137-163); callers with symbols or values derived from them as the first operand: src/cyclic/decode.rs:128, 131, 223, 240, 326, 333; src/cyclic/owned.rs:338, 341; src/correct.rs:420, 438. Only `Field::Binary`, that is `Field::binary` with anything other than (8, 0x11D) or (11, 0x805); x86-64, rustc 1.99.1, release and LTO builds.
- **Reproduction:** Harness `timing` (docs/audits/AUD-006-harnesses/timing): `cargo build --release --bin timing`, then `taskset -c 3 target/release/timing`. It times `CyclicWords::correct_word` on 2,048 clean all-zero words and on 2,048 random valid words, 41 interleaved rounds. Assembly: `cargo rustc --release --lib -- --emit asm -C codegen-units=1` shows `and %r9d,%r14d; je` (r9d = 1 << degree, r10d = the polynomial) in the Binary arm of `Field::multiply`, and the same four times in `Field::inverse`; an LTO program built as RUST-12 asks (panic = abort, codegen-units = 1) shows the same jumps.
- **Expected behavior:** src/field/binary.rs:1-3: products and inverses use "masks and fixed chains, never tables or branches on an element"; src/correct.rs:3-4: "The arithmetic never branches on shard bytes"; docs/TECHNICAL.md limits decoder timing to error-dependent results. The register marks AUD-002-SEC006 verified because "the claim covers … single products and inverses".
- **Observed behavior:** For GF(2^10) made by `Field::binary`, checking a word that has no errors takes 2.84 to 2.86 times as long for random words as for all-zero words (two runs of the reviewer, one of the coordinator). For the named GF(2^11) the ratio is 1.00 (0.98 to 1.03). The named fields' arms use shifts, SIMD and conditional moves.
- **Impact:** A process that shares the CPU can learn about the symbols of data a program handles in a field of its own choice, through timing and branch-predictor state; the strict mode accepts such fields. QR codes (GF(2^8)) and MHFE-REPAIR-1 (GF(2^11)) are not affected. No symbol was recovered; only the dependence was shown. The named fields are branch-free because of today's code generation, and no check holds them so. A regression of AUD-002-SEC006.
- **Evidence:** Harness `timing`; reviewer's assembly listings (machine-local); coordinator's rerun: GF(2048) 2,043/2,042 ns, ratio 1.00; GF(2^10) 2,110/6,012 ns, ratio 2.86.
- **Recommended fix:** Keep the reduction mask opaque to the optimiser in src/field/binary.rs (`core::hint::black_box`, or reduce at a fixed bit position after shifting the element left by 16 − m), and add a check that keeps every arm free of jumps on operand bits. Until then, state the limit in docs/TECHNICAL.md and SECURITY.md, and correct the comments at binary.rs:1-3 and correct.rs:3-4.
- **Required verification:** The timing harness gives a ratio near 1.00 for GF(2^10); the release and LTO assembly of `Field::multiply` and `Field::inverse` shows no jump on an operand bit in any arm.

#### AUD-006-BLD001 — High — Publishing this tree would put a second, unsigned 0.1.0 under the version that the signed GitHub release and the deleted crates.io upload already hold

- **Category:** BLD.
- **Severity:** high.
- **Status:** open.
- **Release blocking:** true. The package that would be uploaded is not the signed and attested one, and the version is taken.
- **Affected files and builds:** Cargo.toml:3 (`version = "0.1.0"`); CHANGELOG.md:3-7 (an Unreleased entry above 0.1.0); docs/API.md:33 and README.md:60 (instructions and figures for 0.1.0).
- **Reproduction:** `cargo package --offline --locked --allow-dirty --no-verify` gives reed-solomon-core-0.1.0.crate with SHA-256 b2296a6d54b031ac93954617fecd9fa4bde3d853ca98ca16798dbd5790bbed32. The GitHub release v0.1.0 asset has SHA-256 6eadca15712b550f8a4bc7cf6cd232023dd4726d61095dfaa23caf22bae19be8, attested by release.yml run 43804427212 at a55d636. The deleted crates.io upload was 552e69cc…, and the local crates.io index cache still lists 0.1.0 (published 2026-11-16T03:48:14Z). The publish dry run (publish-dry-run.log) packaged 0.1.0 and reached "Uploading" without a warning.
- **Expected behavior:** One version, one archive: a crates.io package equals the signed and attested archive of its version, or carries a new version with its own tag, signature and attestation (CHECK-BLD-005).
- **Observed behavior:** 8 of the 87 packaged files differ from the signed archive: the normalised Cargo.toml and Cargo.toml.orig (the dependency requirements), .cargo_vcs_info.json, CHANGELOG.md, README.md, SECURITY.md, docs/API.md and docs/README.md. The documented `gpg --verify reed-solomon-core-0.1.0.crate.asc` step would fail on it, and neither SHA256SUMS nor the attestation covers it.
- **Impact:** Three byte-different archives would carry the name reed-solomon-core 0.1.0; crates.io does not let a version be replaced or used again, so the upload would be refused, or, were it taken, a lock file pinned to the deleted upload would fail its checksum. The code (src/, tests/, examples/, Cargo.lock) is the same in all three.
- **Evidence:** Release reviewer's package comparison and digests (machine-local); publish-dry-run.log; the GitHub release and attestation API, read only.
- **Recommended fix:** Release this tree as 0.1.1: a dated CHANGELOG heading, the 0.1.0 references at docs/API.md:33 and README.md:60 updated, a commit, a signed tag v0.1.1, the attestation of release.yml, and `cargo publish` from a clean checkout of that tag.
- **Required verification:** `cargo package` of the tag gives the attested digest; after the upload the crates.io index `cksum` equals it; the documented `gh attestation verify` command passes.

#### AUD-006-BLD002 — Low — The release workflow attests a tag without running the CI gates

- **Category:** BLD.
- **Severity:** low.
- **Status:** open.
- **Release blocking:** false.
- **Affected files and builds:** .github/workflows/release.yml:3-5 and 23-36; .github/workflows/ci.yml:5-9.
- **Reproduction:** Static review: release.yml runs on tags `v*` and only runs `cargo package --locked`; it has no `needs:` on CI, no `workflow_call` and no check of CI's result; ci.yml runs on branches, pull requests and by hand, never on tags; the repository has no rulesets.
- **Expected behavior:** CHECK-BLD-005: the normal release path cannot bypass the mandatory gates.
- **Observed behavior:** A tag on a commit whose CI failed, or never ran, still gets an attested package. v0.1.0 was attested twice (run 43802177681 at 664ebb1, run 43804427212 at a55d636). No bypass happened: CI passed at a55d636 (run 43804427792).
- **Impact:** A broken commit could be released with a valid attestation; the attestation then says where a package was built, not that it passed the tests.
- **Evidence:** release.yml and ci.yml, read; the GitHub API, read only.
- **Recommended fix:** Make ci.yml callable (`workflow_call`) and let the packaging job depend on it, or check CI's conclusion for `$GITHUB_SHA` before packaging.
- **Required verification:** Static review of release.yml.

#### AUD-006-BLD003 — Low — The compatible requirements are explained by a one-copy promise they do not decide, and drop CORE-25's exact pins for what secret safety rests on without a recorded reason

- **Category:** BLD.
- **Severity:** low.
- **Status:** open.
- **Release blocking:** false.
- **Affected files and builds:** Cargo.toml:26-38 and CHANGELOG.md:5-7 (working tree); docs/audits/README.md rows AUD-001-BLD002 and AUD-002-SEC005.
- **Reproduction:** Probes of the security reviewer (harness `one-copy` and machine-local variants): a library requiring `secret-protection-core = "=0.1.0"` and a program requiring `"0.1"` also build one copy (one lock entry, equal `Secret` TypeIds); a library pinning `libc = "=0.2.190"` with a program needing 0.2.191 fails to resolve; the protection crate taken by the program from a path and by this crate from the registry gives two copies under caret requirements too (two lock entries, two `before_main` entries in `.init_array`, `E0277: Secret: Held is not satisfied`); with secret-protection-core 0.1.0, a program requiring zeroize 1.9.2 fails to resolve.
- **Expected behavior:** CORE-25: a library on crates.io takes caret requirements, and "only what the protocol or the safety of secrets rests on stays exact"; the changelog says what a change does.
- **Observed behavior:** sha2, zeroize and secret-protection-core became caret requirements. The changelog's reason, one copy of the protection crate, holds with exact pins too, and fails with a path or git source either way. What the change does give is that a program can resolve a later 0.1.x and the fixes of the dependencies. Cargo.lock still holds secret-protection-core 0.1.0 and zeroize 1.9.1, while 0.1.1 is out.
- **Impact:** No secret is affected today. From the next 0.1.x on, a program may run the strict mode with a protection crate that this crate's strict tests did not run with; the changelog misleads a program built from sibling checkouts.
- **Evidence:** Probes and their output (machine-local); harness `one-copy`.
- **Recommended fix:** Reword the changelog and the Cargo.toml comment to say what the requirements do; record the reason for leaving CORE-25's exception; require secret-protection-core "0.1.1", update Cargo.lock and fuzz/Cargo.lock, and run the strict tests with them before publishing.
- **Required verification:** Review of the text; the strict tests pass with the new lock files.

### Informational observations and recommendations

- MHFE-REPAIR-1: all 16 cards (sizes 2, 4, 6 and 8 of four containers) and all 3 repairs of mhfe_spec's vectors/profiles/repair-words.json (SHA-256 fa4f77a5…, as its SHA256SUMS says) come out of `CyclicCode` and `CyclicWords` as published, by five paths each for the repairs. Against mhfe_core's own decoder (src/repair/field.rs, copied into the harness), 24,000 random containers of 12 to 24 words, every card size and damage up to 2e + s = k + 2 gave the same parity and the same decoding in every case (17,634 words found, 1,501 of them beyond the bound by both; 6,366 found by neither).
- One copy of secret-protection-core: a program that takes this crate (path, default features) and `secret-protection-core = "0.1"` from crates.io builds one copy: one lock entry, one `before_main` in `.init_array`, the program's `Secret` accepted as `Held`. The crate never calls `Isolation::enter*`, `Worker`, `serve` or `write_secret`; after a program isolates itself, a strict encode still works. Two copies arise only from a path or git source, or from an incompatible 0.2, and then fail safe at compile time.
- secret-protection-core 0.1.1 (crates.io, 2026-11-24) changes only its manifest (no change under src/ since 0.1.0) and takes caret requirements for its own dependencies.
- The two RustSec warnings (instant 0.1.13, lru 0.7.8) come only through the test oracle reed-solomon-erasure 6.0.0; no normal dependency has them.
- The suite's independent oracle, reed-solomon-erasure 6.0.0, covers GF(2^8) and GF(2^16) only; GF(2^11) and the other binary fields rest on literal answers and self-consistency, which the codes harness covered.
- `Code::correct` has no work limit; near 65,536 shards a call may take long (not measured).
- A pile of 200,000 header-only files took about 1,656 bytes of memory per file, mostly unused capacity; a program that accepts many small files from others should cap their number.
- `Correction::Corrected` of the cyclic code counts lost places whose value was already right; docs/API.md says so, the rustdoc does not.
- Coverage reproduced: 98.23 % (5,984 of 6,092 lines), as docs/COVERAGE.md states for the release tree.

### Assessment and limitations

The coding, the correction and the shard files behaved as documented in every probe and gate; no wrong data came back inside a documented bound, and the fuzz targets found nothing. The record supports publishing the crate once AUD-006-BLD001 is resolved by a new version, and once AUD-006-SEC001 is fixed or its limit stated. It does not certify the absence of defects.

- Linux x86-64 only: macOS, Windows, Android, iOS and WebAssembly were not run natively; CI on GitHub runs the tests on Linux AArch64, macOS and Windows.
- Constant-time behaviour was checked on x86-64 with rustc 1.99.1; AArch64 was not checked.
- The OpenPGP signatures and SHA256SUMS of the GitHub release were not downloaded or verified; the attestation was read through the API.
- Forced allocation failure part-way through a call, Miri, and statistical timing tests beyond the interleaved probe were not run.
- secret-protection-core was reviewed only where this crate uses it.
- Three reviewers were interrupted by a restart of the coordinating session and resumed from their saved context; the snapshot was checked unchanged before and after.
- This is an AI-assisted review, not an independent human security audit.
