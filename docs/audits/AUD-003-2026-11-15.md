The public strict-mode interface still performs some payload operations on the caller’s stack and returns a computed secret-derived digest in an ordinary error. The startup self-test can also abort on a refused allocation.

## Findings and required fixes

### AUD-003-SEC001 · Removing files can compare shard payloads on the caller’s stack

A strict set retains two copies of the same shard. Calling without with both copies retained invokes duplicate resolution. The strict wrapper calls the ordinary method directly. Duplicate resolution compares the surviving payload slices on that thread. The operation can process payload bytes without satisfying the strict stack conditions. Mapping protection on the original buffers does not cover those temporaries.

**Source:** src/strict/files.rs:248–249; src/file/set.rs:567–577; src/file/set/shards.rs:169–173,277,317.

**Fix and verify.** Move the recomputation into strict(...) or restructure it to use verified public metadata only. Cover retained duplicates with and without a protected stack; require refusal before comparison if a stack cannot be admitted.

### AUD-003-SEC002 · Lazy block and survey checks escape the strict reader

Observe the return types of strict::read and strict::Pile::readings, then trace block() and survey() on a valid file. The returned ShardFile is the ordinary reader. block() and survey() compute CRC over the payload on the caller thread and do not enter the protected stack. Reading a block or inspecting a file can process secret data outside the advertised boundary. The initial buffer remains protected.

**Source:** src/strict/files.rs:102–104,129–131; src/file/reading.rs:150–174; src/file/crc32c.rs:17–25.

**Fix and verify.** Provide a strict reader with guarded lazy operations or validate/cache the required state inside the strict operation. Keep the lifetime/owner restriction explicit for any borrowed view. Cover both reader entry points, repeated calls, absent stack admission and accepted ordinary file shapes.

### AUD-003-SEC003 · Reading a correction’s location also decodes the original and replacement symbols

Read the public position/kind through get or the iterator of a strict plan, without requesting its values. get calls record and decodes both u16 fields. In local unoptimized Linux LLVM IR it reserves a 24-byte ordinary stack slot and passes it as the record return destination before projecting metadata. An application can materialize recovery-word values in ordinary temporary storage merely by showing a position. This does not depend on the callback retaining a copy.

**Source:** src/correct/changes.rs:58–63,101–105,164–188,231–233; tests/suite/strict.rs:111.

**Fix and verify.** Have get decode only the position/kind offsets. Provide a strict plan view if ordinary symbol access is otherwise accidentally exposed. Inspect a debug build for symbol loads on metadata-only access and cover get, iter and IntoIterator; verify the separate value accessor remains guarded.

### AUD-003-SEC004 · Strict recovery returns the computed digest in an ordinary printable error

Trace the existing digest-mismatch branch in rebuild and rebuild_into; inspect the type and formatting of the forwarded error. SetError::Digest carries both the stated hash and the actual hash of the reconstructed data. The latter differs from the public header; derived Debug prints all 32 bytes. The strict wrapper forwards that value from the protected-stack job. A log or crash report can include a stable fingerprint of the reconstructed bytes. This matters especially for partially known or low-entropy material. No memory dump or leak was measured.

**Source:** src/file/set.rs:124,159–163,423–430; src/strict/files.rs:207–218; secret-protection-core 0.1.0 src/os/unix.rs:752–762,781–784.

**Fix and verify.** Map mismatches to a status-only strict error before returning from the protected closure. Keep detailed diagnostics confined to the portable API where appropriate. Cover mismatches through both strict APIs; verify the error payload and Debug output contain no computed digest and output handling still follows the documented policy.

### AUD-003-DOC001 · The strict-mode example populates unchecked secret buffers

Follow the README’s strict-mode input and callback-destination construction under best-effort allocation. The example fills Secret::with_capacity before checking its properties. The callback destination is also created with with_capacity and captured by the closure; strict::values checks the Changes buffer, not that destination. The sample can put an input or recovered word into unlocked memory despite its comment describing protected output. The published example uses public constants; the risk is for applications following it with real input.

**Source:** README.md:251–254,261–271; src/strict/codes.rs:223–229; upstream src/protect.rs:61–75.

**Fix and verify.** Show a checked helper that allocates, confirms lock/fork/dump properties for the supported platform, and only then accepts bytes. On Apple document the separate process-wide measure. Exercise the documented path under a small lock budget and check that neither caller-supplied destination nor input is populated when its required protection is absent.

### AUD-003-FUN001 · for_data validates digest-specific size after it hashes the input

Trace for_data with DataDigest::Sha256 for a descriptor accepted without a digest and rejected with one. The first new call passes None; Some(sha256(data)) is evaluated before the second constructor validates the digest-bearing shape. The documented ordering is wrong for sizes beyond the digest bound; the metadata decoder itself rejects them correctly. No impractically large payload was tested.

**Source:** src/file/facts.rs:85,102–122.

**Fix and verify.** Validate the digest-bearing layout with a placeholder before hashing, then set the computed digest in the validated facts. Test ordering at the metadata boundary using a counting digest hook or a separate shape-validation helper without allocating a giant message.

## Integration and remaining limits

The release pin is correct. The upstream 0.1.0 crate, source commit and both lockfiles agree; the earlier mutable-Git-reference finding AUD-001-BLD002 is verified.

The strong digest binding and stale-plan refusal now precede mutations for both RS code forms. A retained callback may intentionally copy returned data; the application is responsible for that copy.

The Apple policy waives per-page dump exclusion and does not require an Isolation report. A consumer requiring dump exclusion must confirm the appropriate process-level protection before handing over secrets. Strict payload calls refuse on Windows/WASM; metadata-only constructors may still succeed.

An ordinary fork between strict calls invalidates the assumption behind already parsed views. Pile stores borrowed slices, not fresh owners to recheck. Follow upstream’s no-fork rule while a protected stack is active and discard/reparse cached reader/set views in a child. This is a lifecycle limitation under the documented prohibition on using parent buffers in the child; it is not evidence of inherited secret data.

The currently inspected stego-core checkout uses reed-solomon-core from Git f6e2888 and secret-protection-core from Git fb2a6d3. No reed-solomon-core dependency was found in the inspected MnemoCode Rust manifests or lockfile. This audit establishes no consumer upgrade.

Runtime acceptance is Linux x86-64 only. Windows, macOS and WASM were cross-checked. Android, iOS, Windows, macOS, ARM64 Linux and WASM were not executed in this audit. No GitHub run was dispatched for the working tree.

No new line-coverage measurement. The README value of 98.35% is historical. No claim was made about seeing a secret in swap, a core dump or an external process.

The long opt-in field proof was ignored in the ordinary profile tests. No independent five-target fuzz replay; the supplied post-pin logs are retained separately.

The callable lifecycle checks concern public synthetic data. The 32-bit empty-request case and extreme SHA limit were checked from code and representable geometry, without allocating giant messages. Unoptimized Linux IR was inspected at the affected metadata reader; this was not a multi-architecture assembly review.

The register uses snapshot SHA-256 in lieu of a fix or verification commit. The frozen brief excludes edits to the checkout; this Markdown/JSON pair, register and evidence are delivered outside it.
